# Production Security Controls

## Application boundary

- Authentication uses Argon2 password hashing, short-lived bearer tokens, rotating `HttpOnly`, `Secure`, `SameSite=Strict` refresh cookies, and origin checks for cookie-bearing refresh and logout requests.
- Login attempts are limited per account and source IP: five attempts per five minutes, followed by a progressive lockout. Password-reset requests are limited to three per 15 minutes.
- Every `/api/` request is limited per client IP to 300 requests per minute. Redis is the authoritative counter. A deployed API returns `503` rather than serving unprotected traffic if this dependency is unavailable.
- Requests larger than 5 MiB are rejected before route processing. File uploads must remain disabled until they have a dedicated endpoint that validates type, size, content, storage key, malware scanning, and authorization.
- Pydantic API models reject unknown fields, preventing mass assignment. SQLAlchemy ORM bindings are used for application queries; direct SQL is limited to the fixed health-check query.
- Access checks resolve customer-scoped records before reads and mutations, so guessed identifiers do not bypass authorization. Public certificate verification uses an unguessable token-scoped route only.
- Object storage keys are normalized under an application-owned prefix. No user-controlled filesystem path is used for persisted files.
- The React clients render data through React, not raw HTML injection. Do not introduce `dangerouslySetInnerHTML`, `eval`, dynamic imports from user input, or server-side URL fetching without a reviewed allowlist.

## Browser and HTTP protections

- API responses set `Content-Security-Policy`, `Strict-Transport-Security` in deployed environments, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, and `X-Frame-Options: DENY`.
- CloudFront applies the equivalent headers to static applications. The CSP includes `frame-ancestors 'none'`; `X-Frame-Options` is retained for legacy clients.
- Static and API CSP permits inline styles only because the existing frontend requires them. Inline scripts are not allowed. Remove `unsafe-inline` from `style-src` after migrating inline styles to hashed or external stylesheets.
- CloudFront sends a random origin header to the ALB API origin. ECS receives the same secret from Secrets Manager and refuses non-health requests without it. `SECURITY_EDGE_SHARED_SECRET` is a deployment invariant outside local/test.
- Client identity: behind CloudFront and the ALB the socket peer is the load balancer, so every per-client control (global API rate limit, browser-login IP limit, persisted login/refresh/password-reset IPs) uses one resolver, `core/client_identity.py`. CloudFront appends the viewer address to `X-Forwarded-For` and the ALB (`xff_header_processing_mode = "append"`) appends CloudFront's, so the viewer is the entry `SECURITY_TRUSTED_PROXY_HOPS` (2) from the right; everything to the left is attacker-controlled and is never used. Forwarded values are honoured only when the request also carries the valid edge secret. Otherwise, or if the chain is shorter than expected or malformed, the socket peer is used, so a forged header can only make an identity less specific. IPv6 limiters key on the /64. `SECURITY_TRUSTED_PROXY_HOPS` defaults to 0 (never trust the header) and requires `SECURITY_EDGE_SHARED_SECRET`. It is set only on the API task. If the number of proxies in front of the API changes, change it together with that topology.
- Audit redaction: `append_audit_event` replaces credential values (password and password-hash fields, MFA secret ciphertext, token/recovery digests and any `*_secret`, `*_token`, `*_ciphertext` key, at any depth) with `[REDACTED]` before hashing, so new events never contain them. `GET /admin/audit-events` applies the same redaction on output, so historical rows written before this change are not returned with secrets. Stored rows are never rewritten, which keeps the audit hash chain intact; the credentials already in historical rows remain in the database until a separately approved retention decision.
- Request observability: every HTTP request gets a server-generated `X-Request-ID` (an inbound value is ignored) and one JSON log line on stdout (`request.completed`, or `request.failed` with exception class and call-site frames only). Fields: request ID, method, matched route template (never the raw URL), status, duration, and the canonical client IP. Query strings, headers, cookies, bodies and exception messages are never logged, and uvicorn's access log, which prints query strings, is suppressed in favour of this line. Unhandled errors return a JSON 500 that quotes only the request ID. Uvicorn's own per-request `Exception in ASGI application` traceback, which includes the exception message, is dropped; other `uvicorn.error` records (startup, lifespan, configuration, protocol errors) are kept. Limit: failures raised before routing log the path as `(unmatched)`.
- Certificate artifact durability: the PDF write to object storage cannot be rolled back with the database, so issuance writes the PDF, reads it back and compares its SHA-256 before any row refers to it, and removes the object if anything after the write fails. Regeneration of a legacy PDF takes a row lock, writes a new write-once key (`...-r1.pdf`, `-r2`, ...) and repoints the row in the same transaction; the committed artifact is never overwritten and superseded revisions are kept. A crash, or a commit that fails, cannot run in-process cleanup and can leave an unreferenced object; `python -m hms_backend.app.tooling.reconcile_certificate_artifacts` reports those. It classifies every unreferenced object older than `--older-than-minutes` as `orphan` (an issuance whose certificate row does not exist, or a regeneration attempt newer than the certificate's current revision), `superseded` (an older revision of a successfully regenerated certificate, which is committed history) or `unclassified` (a key outside the certificate key scheme). It is a dry run by default; `--apply` deletes **only** `orphan` objects, and never the other two. Because regeneration reuses an `-rN` key after a rolled-back attempt, each deletion takes the same certificate row lock regeneration takes, re-checks the object under it, and holds the lock until the delete finishes, so a key adopted by a regeneration after the scan is skipped. The age threshold is only a safety buffer for issuance orphans (whose row does not exist and so cannot be locked); it does not by itself guarantee that no transaction is still open. Deleting superseded revisions would be a separate retention decision. The task role already has `s3:DeleteObject` and `s3:ListBucket` on the media bucket.
- Sync correctness: the change feed is read with a cursor (`seq > since`), which is only correct if sequence order equals commit order. A sequence number is allocated at INSERT, so `stage_sync_change` (`core/sync_ledger.py`) takes the global ledger lock **before** inserting a `SyncChange` and holds it to the end of the transaction; every writer goes through it (a test forbids constructing `SyncChange` anywhere else), so a client can never advance its cursor past a change that commits later. Sync devices are bound to the user who registered them: a request for a device registered to another user is refused with 403 instead of silently re-pointing it. The device row is locked (`SELECT ... FOR UPDATE`) for the duration of each sync request, so a revoke or metadata update serialises with in-flight syncs and a request that starts after a revoke commits sees it, and concurrent first registrations of one device id resolve to a single row instead of an error. Requests from the same device are therefore processed one at a time. The inspector browser therefore keeps one device id **per signed-in user** (`hms.inspector.device-id:<user id>`), never one per browser profile, and has no literal fallback shared between users (without usable storage it uses a random per-page id), so inspectors sharing a profile are not locked out by the ownership check. Notification outbox `aggregate_id` is 36 characters, so a longer device id (the inspector browser's is 54) is mapped to a stable UUID rather than failing the request.
- Notification delivery: an email or SMS cannot be rolled back, so a dispatcher **claims** a message before sending it (`modules/notifications/claims.py`, used by both the notification dispatcher and the password-reset email dispatcher). The claim is one atomic `UPDATE ... WHERE status = 'PENDING' AND due` that moves the row to `SENDING`, increments `attempts` and sets `scheduled_for` to a lease deadline (`NOTIFICATION_CLAIM_LEASE_SECONDS`, default 300, which must exceed the slowest provider call; adapters time out at 30 s), committed before the send. Only the holder of a claim sends, so overlapping beat ticks, parallel workers and redelivered acks-late tasks cannot send the same message. The outcome is written fenced by the claim (`attempts` is the fencing token), so a worker whose lease expired cannot overwrite a newer claim, and a transient database failure while recording it is retried instead of leaving a sent message to be sent again. A raising adapter counts as a failed attempt (only the exception class is stored). Limit: if a worker dies after claiming, the outcome is unknown; when its lease expires the message is requeued (at-least-once, so a duplicate is possible in that window and a message is never silently dropped) or, once its attempts are used, dead-lettered with any reset-token envelope scrubbed. The relay locks each outbox event (`FOR UPDATE SKIP LOCKED`) so two relays do not both process it. No schema change: `SENDING` is a new status value. A password-reset email whose token has since been superseded by a newer request is dead-lettered with its ciphertext scrubbed and not sent, because the API rejects a superseded token on confirm; the check runs once after the claim, so a supersession landing between that check and the send is not caught.
- Delivery receipts: a provider can report delivery before the dispatcher has stored the `provider_message_id` the receipt is keyed on (even before `send` has returned), and the webhook answers 2xx so the provider does not retry. A receipt that matches no notification is therefore parked as an outbox row of type `DELIVERY_RECEIPT` (deduplicated on provider id and status, so a provider retry parks it once) instead of being dropped, and the relay applies parked receipts in the order received once their notification is identifiable, before it handles notification events. Parked receipts never share the notification-event batch, so they cannot delay real events. Each sweep selects only receipts that are ready (their notification now carries the provider id) or expired, never "the oldest N", so a receipt that is merely waiting cannot occupy the sweep and starve a ready one. A receipt that still matches nothing after `NOTIFICATION_RECEIPT_RETENTION_HOURS` (default 48) is retired unapplied. A notification may therefore read `SENT` for up to one relay interval (30 s) after the provider has reported `DELIVERED` or a bounce. No schema change.
- Retest scheduler: reminders fire on an exact day (due today, N days before, N days overdue), so a run that fails is not made up the next day. The daily run is therefore single-flight on PostgreSQL (`pg_try_advisory_xact_lock`): an overlapping run (a redelivered acks-late task, a second beat) returns `skipped_concurrent` instead of racing the first. Event creation tolerates another transaction creating the same dedupe key (a savepoint, so the loser skips it instead of failing the whole run), schedules are processed in a fixed order so two runs cannot deadlock on unique-key locks, and each schedule runs in its own savepoint so one that cannot be processed is skipped and counted in `failed` without discarding the day's other reminders. The run's summary reports `emitted`, `failed` and, when it steps aside, `skipped_concurrent`. Limit: a day on which no run completes (beat or worker down at 07:00 UTC) is still not caught up.
- Notification readiness: before worker/beat are started against a database, `python -m hms_backend.app.tooling.notification_readiness` (run in DEV by the manually dispatched `Verify AWS Dev Notification Readiness` workflow as a one-off task on the current `hms-dev-migrate` definition) reports from aggregates only whether the rows the dispatchers will meet are ones they are designed for. It has no mutation mode: every query runs in a PostgreSQL `READ ONLY` transaction that is verified before use and always rolled back, with a statement timeout. The report holds counts, statuses and ages, never addresses, subjects, bodies, payloads, ciphertext, tokens or error text. Blockers (exit 1): expired `SENDING` claims on notifications or password-reset deliveries, and `SENT` or `DEAD_LETTER` password-reset rows retaining ciphertext. Due `PENDING` work and unprocessed outbox events are warnings (they will be sent or relayed on activation). `outbox.processed_with_error` is diagnostic only and never gates: a business event that failed once then succeeded, and a receipt retired as unmatched, legitimately end processed with an error. The report also carries an activation preview for human review, never a gate: unprocessed outbox events by event type (count, oldest and newest age), by aggregate type, and by event-type and aggregate-type pair (at most 50 pairs), and due `PENDING` password resets classified in the dispatcher's own order (`not_selected_ciphertext_missing`, `reset_token_missing`, `consumed`, `expired`, `user_unavailable`, `valid_superseded`, `valid`). Only `valid` and `valid_superseded` rows result in an email; `consumed`, `expired` and `user_unavailable` are dead-lettered unsent, and `not_selected_ciphertext_missing` rows are never selected by the dispatcher (it only picks `PENDING` rows with ciphertext) so they stay `PENDING` untouched. Type names are restricted to identifier-shaped values, and no identifiers, addresses, payloads, tokens or error text appear. Exit 2 means the check itself failed. Limit: the workflow gates on the task's exit status; the JSON report is read from the migrate CloudWatch log stream, because the GitHub deploy role has no log-read permission.
- CloudFront is TLS-only for viewers. The current development ALB origin is HTTP because it has no custom DNS name or ACM certificate. The Terraform domain inputs atomically enable an ALB HTTPS listener, HTTP-to-HTTPS redirect, CloudFront `https-only` origin policy, and Route 53 aliases only when every required value is supplied.
- Configure `public_root_domain`, `staff_hostname`, `api_origin_hostname`, `public_hosted_zone_id`, `alb_acm_certificate_arn`, and `cloudfront_acm_certificate_arn` together. The ALB certificate must be issued in `ap-southeast-2` for `api_origin_hostname`; the CloudFront certificate must be issued in `us-east-1` for `staff_hostname`. Terraform creates no ACM certificates, so request and DNS-validate them manually before setting the ARNs.
- `staff_hostname` aliases to CloudFront and is the only public application/API base URL. `api_origin_hostname` aliases to the ALB solely so CloudFront can validate the ALB certificate. Direct API-origin traffic lacks the CloudFront secret and is rejected, except for narrowly scoped health endpoints.

## AWS traffic protection

- CloudFront provides TLS termination, caching, and edge absorption for static traffic.
- `enable_waf` is an explicit Terraform switch. When enabled, the ALB receives AWS WAF Common Rule Set protection and a 2,000-request-per-IP rolling five-minute rate rule. WAF has a monthly cost and is intentionally disabled in low-cost development until approved.
- WAF protects against common malicious traffic and high-volume abuse. It does not replace application authorization, scoped database access, CSRF controls, validation, or rate limits.
- AWS Shield Standard is included with AWS services. Use CloudWatch alarms and WAF sampled requests to investigate bot or DDoS events; do not rely on access logs for secrets.

## Supply chain and operations

- GitHub Actions are pinned to immutable commit SHAs. Dependabot opens weekly updates for actions, Python, and npm dependencies; updates require CI review before merge.
- Backend containers install from `uv.lock` with `--locked` and both backend and certificate images run as non-root users.
- `npm audit --omit=dev` is clean for both web applications. Run `uv lock --check`, Python test/lint/type checks, Terraform validation, and container builds in CI before deployment.
- Generic provider webhook secrets fail closed outside local/test, use constant-time comparison, and are accepted only in a request header. Twilio callbacks verify `X-Twilio-Signature` against the exact configured public callback URL. SES/SNS callbacks verify the provider signature, a trusted SNS topic ARN, and an HTTPS AWS SNS signing-certificate URL; certificate retrieval rejects redirects and arbitrary hosts to prevent SSRF.

## Production release checklist

1. Set `enable_waf=true` only after approving the WAF cost and monitor the rule in count mode during the first release if application traffic is not yet known.
2. Create a public Route 53 zone, request and DNS-validate the ACM certificates in the required regions, then set all six custom-domain Terraform inputs together. Confirm `https://<staff_hostname>/api/...` works before any DNS cutover; do not expose the API-origin hostname to application clients.
3. Keep `AUTH_BROWSER_COOKIE_SECURE=true`, `AUTH_BROWSER_ALLOWED_ORIGINS` exact, and all generated application secrets in Secrets Manager.
4. Configure log retention and alarms for WAF blocks, repeated 401/429 responses, failed sign-ins, unusual API request rate, and infrastructure health.
5. Before configuring Twilio live delivery, set its exact HTTPS status callback URL in both Twilio and `NOTIFICATION_TWILIO_STATUS_CALLBACK_URL`. Keep `NOTIFICATION_CHANNEL_MODE=console` until the sender identity and callback endpoint are ready.
